## Порівняння підходів до стилізації (ПР № 6)

Для цього проєкту класичний підхід із CSS-файлами є швидшим і зручнішим, оскільки структура застосунку невелика та не вимагає складного динамічного стилювання. Проте використання Styled Components показало значні переваги при роботі з пропсами: ми змогли легко змінювати колір пріоритету без написання додаткових CSS-класів. У майбутньому для масштабованого React-проєкту варто обирати Styled Components за відсутність конфліктів імен та високу гнучкість.

## Файл даних

- **Розташування**: Файл даних `tasks.json` розташований у папці `data/` в корені проєкту (`data/tasks.json`).
- **Поведінка при відсутності**: Якщо файл відсутній, застосунок автоматично створює його разом із необхідною папкою (завдяки `{ recursive: true }`) та записує туди порожній масив `[]`.
- **Прапорець `wx`**: Використовується прапорець `wx` при відкритті/створенні файлу (`fs.open`). Він гарантує, що файл буде відкрито лише для запису, а якщо файл вже існує — операція завершиться помилкою і не перезапише існуючі дані користувача.
- **Початковий вміст**: При створенні нового файлу записується демонстраційне завдання з полями `id`, `title`, `completed`, `dueDate`, `priority`, відформатоване за допомогою `JSON.stringify(..., null, 2)`.

## Формат і запис даних

Дані застосунку зберігаються у файлі `data/tasks.json` у вигляді масиву JSON-об'єктів із полями `id`, `title`, `completed`, `dueDate` та `priority`. Запис і читання файлу виконує React-застосунок у середовищі NW.js за допомогою асинхронного Node.js API `fs.promises`. Файл записується з відступами у 2 пробіли (`JSON.stringify(tasks, null, 2)`), щоб зберегти чітку структуру текстового файлу та забезпечити зручне відстеження змін у версіях Git.

## Обробка помилок

Застосунок коректно обробляє типові збої файлової системи під час роботи з `data/tasks.json`: якщо файл відсутній, він автоматично створюється заново зі стартовим шаблоном без переривання роботи. У разі пошкодження структури JSON (наприклад, через синтаксичну помилку або маркери конфлікту Git) чи відсутності прав доступу на читання/запис (`EACCES`, `EPERM`) користувач бачить зрозумілий червоний банер із поясненням причини збою. Якщо зчитування файлу завершилося невдачею, застосунок переходить у режим «безпечної відмови» — блокує форму додавання та зміну стану завдань. Це гарантує, що порожній список на екрані випадково не перезапише пошкоджений файл і не знищить наявні дані користувача.
